## PROJECT CONTEXT (read this first)

You are building **PactScan AI**, an agentic GraphRAG platform for legal contract compliance, scoped to SaaS/vendor Data Processing Agreements under India's DPDP Act (primary regulation; GDPR secondary). This is **Phase 5** of a 7-phase build. By now you have: Phase 1's Detect Agent, Phase 2's Suggest Agent, Phase 3's Fix & Learn (`approvals`, `document_versions`, `audit_log` tables), and Phase 4's Ask Agent. All prior phases hardcoded `tenant_id = "demo_tenant"` and had no real authentication. All LLM calls go through `backend\app\llm\client.py` (Google Gemini, caching + 7-tier model chain + multi-account fallback across 3 accounts) — no changes to that abstraction are needed in this phase. The real `.env` lives only at `backend\.env`.

**What Phase 5 must prove:** the system supports real login with role-based access (end-user vs. reviewer/admin), a dashboard visualizing data already generated by Phases 1-3 (nothing new computed — read-only visualization layer), and real-time notifications firing when new findings are created.

**Simplification note:** full Auth0/Clerk SSO integration is a "designed but not built" item for this build. Build a simple, real email/password login with hashed passwords and JWT session tokens — sufficient to demonstrate role-gating.

## STEP-BY-STEP BUILD INSTRUCTIONS

### 1. Extend the PostgreSQL schema (`backend\app\db\models.py`)
- **`tenants`**: `id`, `name`, `created_at`. Insert one row for `"demo_tenant"` matching Phase 1-4's hardcoded value.
- **`users`**: `id`, `tenant_id` (FK), `email`, `hashed_password`, `role` (`end_user` / `reviewer` / `admin`), `created_at`.
- **`notifications`**: `id`, `tenant_id`, `finding_id`, `severity`, `message`, `is_read` (boolean, default false), `created_at`.

### 2. Build auth endpoints (`backend\app\api\auth.py`)
- `POST /api/auth/register` — accepts email/password/tenant_id, hashes the password, creates a `users` row. Seed at least 2 demo users on startup: one `end_user` and one `reviewer` role, both under `tenant_id = "demo_tenant"`, with known test credentials documented in the README.
- `POST /api/auth/login` — accepts email/password, verifies against the hash, returns a JWT containing `user_id`, `tenant_id`, and `role` as claims, with a reasonable expiry (e.g., 24 hours).
- Build a FastAPI dependency (`backend\app\api\deps.py`) — `get_current_user()` — that extracts and verifies the JWT from the `Authorization: Bearer <token>` header, and `require_role(["reviewer", "admin"])` for role-gated routes.

### 3. Retrofit tenant scoping into every existing endpoint from Phases 1-4
Go back through every endpoint built so far (`/api/detect`, `/api/suggest/*`, `/api/approvals/*`, `/api/ask`) and:
- Replace the hardcoded `tenant_id = "demo_tenant"` with the `tenant_id` extracted from the authenticated user's JWT via `get_current_user()`.
- Add `require_role(["reviewer", "admin"])` specifically to `POST /api/approvals/{id}/decide` — an `end_user` role must not be able to approve/reject, only view and request.
- Write a test proving an `end_user`-role JWT gets a 403 when calling `POST /api/approvals/{id}/decide`, and that a `reviewer`-role JWT succeeds.

### 4. Build the notification-firing hook (`backend\app\agents\notifications\notify.py`)
- Add a call to this function at the end of Phase 1's Detect pipeline, right after a new finding is written — insert a `notifications` row (`severity` from the finding, a short human-readable `message` including the document name and page).
- Only `HIGH` severity findings should also (optionally) trigger the email stretch-goal send; `MEDIUM`/`LOW` should only create the in-app row.

### 5. Build notification endpoints (`backend\app\api\notifications.py`)
- `GET /api/notifications?unread_only=true` — list notifications for the current user's tenant.
- `POST /api/notifications/{id}/mark-read` — mark a notification as read.

### 6. Build dashboard data endpoints (`backend\app\api\dashboard.py`)
- `GET /api/dashboard/overview` — returns counts: total contracts, findings by severity, approvals by status.
- `GET /api/dashboard/findings-pipeline` — returns findings grouped by their current stage (new finding → redline suggested → pending approval → fixed & applied → rejected) — derive this by joining `findings`, `redline_suggestions`, and `approvals` on their foreign keys; do not add a separately-maintained status field.

### 7. Frontend — build login, dashboard, notification UI
- **`frontend\app\login\page.tsx`** — email/password form, stores the returned JWT.
- **`frontend\app\dashboard\page.tsx`** — role-aware: `reviewer`/`admin` sees a "Pending Approvals" panel in addition to the general overview; `end_user` sees only the overview + findings pipeline. Use a charting library (Recharts) for the severity breakdown.
- **Notification bell** — small bell icon component in the shared app layout/header, showing an unread count badge, with a dropdown listing recent notifications.
- Protect all existing pages from Phases 1-4 so they redirect to `/login` if no valid JWT is present.
