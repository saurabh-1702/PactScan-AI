recorded here, with the reason.

### Node.js

The machine's default `PATH` node was v16.20.2 (too old for Next.js 16). `nvm4w`
already had **v24.14.1** installed; ran `nvm use 24.14.1` (nvm4w persists this
globally). A standalone `D:\NodeJS LTS\node.exe` (v24.16.0) is also present — both
are fine. `create-next-app@latest` produced **Next.js 16.3.4 / React 19.2.8 /
Tailwind v4** (prompt said "Next.js 14+"; latest is newer).

### Frontend scaffold cleanup

`create-next-app` initializes its own nested git repo and adds `AGENTS.md` /
`CLAUDE.md`. The nested `.git` was removed (this is a single-repo monorepo). The
`AGENTS.md`/`CLAUDE.md` files are re-generated by `next dev` on every run, so they
are committed rather than fought.

### Stale Docker containers from a prior attempt (Phase 0)

Docker had leftover `pactscan-neo4j/postgres/redis` containers and `infra_*`
volumes from an earlier attempt (compose project `infra`). These held no data
relevant to a fresh Phase 0 (no schema/graph exists yet), so they were removed and
recreated cleanly under the `pactscan-dev` compose project. The known native
PostgreSQL Windows service on port 5432 was confirmed present — the container's
`5433:5432` mapping avoids it as intended.

## Phase 1

### Dependency choices / substitutions

| Package | Prompt | Actual | Reason |
|---|---|---|---|
| `reportlab` | `4.2.5` | `5.0.1` | current cp314-compatible release |
| `pytest` | `8.3.4` | `9.1.1` | pulled in by the `pytest-asyncio` bump below; suite passes clean on 9.x |
| `pytest-asyncio` | `0.25.0` | `1.4.0` | `0.25` emits ~15 `asyncio.get_event_loop_policy` DeprecationWarnings per test on Python 3.14 |
| document parsing | `llama-cloud` (`client.parsing.parse`) | `llama-cloud==2.16.0` | The prompt's `client.parsing.parse(...)` call **is** the new `llama-cloud>=1.0` API. The older `llama-cloud-services` package is deprecated (EOL May 2026) and pins `llama-cloud==0.1.46`, which conflicts. We use the new package directly. |
| `python-multipart` | (not listed) | `0.0.32` | required by FastAPI for `POST /api/detect` file uploads |

### Gemini Interactions API — confirmed real

The Phase 1 prompt specifies Gemini's Interactions API (`client.interactions.create`,
`response_format`, `interaction.output_text`). This **does** exist in the installed
`google-genai==2.22.0`. `app/llm/client.py` uses:
`client.interactions.create(model=, input=, system_instruction=, response_format=TextResponseFormat(type="text", mime_type="application/json", schema_=<json schema>))`
then reads `interaction.output_text`. If live testing shows the call shape is off,
`_call_gemini()` in that one file is the only thing to adjust.

### Design choices beyond the prompt

- **`GraphStore` abstraction** (`app/agents/detect/graph_store.py`): an interface with
  `Neo4jGraphStore` (real Cypher, incl. `OVERRIDES*1..3`) and `InMemoryGraphStore`.
  The mocked test suite uses the in-memory store so it needs **no Docker/Neo4j**,
  keeping "mocked = zero env dependency" true (lessons-learned §4). Live tests and the
  running API use Neo4j.
- **Test files**: `test_detect_agent.py` (agent behaviour), `test_detect_api.py`
  (endpoint), `test_llm_client.py` (cache + fallback), `test_detect_live.py`
  (`-m live`). The prompt named only `test_detect_agent.py`.

### Cypher: `size()` not `length()` for variable-length relationship lists

`get_overriders()` first used `length(rels)` on a `-[rels:OVERRIDES*1..3]->` list —
Neo4j 5 rejects this (`length()` wants a Path). Fixed to `size(rels)`.

### LlamaParse `client.parsing.parse` call shape (fixed after first live run)

First attempt passed `output_options={"markdown": True, "include_page_breaks": True}`
and no `expand` → `ValueError: You should provide a non-empty sequence for the
'expand' parameter`. Correct call for `llama-cloud` 2.16:
`client.parsing.parse(tier=<tier>, version="latest", upload_file=file_from_path(path), expand=["markdown"])`.
Response: `result.markdown.pages` — a list of page objects with `.markdown` /
`.page_number` / `.header` (or `.error` on a failed page); fallbacks to
`result.text.pages` then `result.markdown_full` / `result.text_full`.
Parsing tier is `LLAMA_PARSE_TIER` in `.env` (default `fast` — cheapest, no AI).

### `pytest.ini`: `addopts = -m "not live"`

Plain `pytest` runs the mocked suite only; `pytest -m live` overrides addopts and
runs only the live tests. Without this, a plain `pytest` with keys present in
`.env` also ran the live tests and burned quota.

### First live run (2026-09-11): 2 real bugs surfaced, both fixed

1. **429 not caught** — `google-genai` raises `compat_errors.RateLimitError` (not
   `errors.APIError`), so the fallback chain died on the first quota error instead
   of advancing. `_call_gemini` now catches broadly and `_is_quota_error()` checks
   class name / status code / message markers. (known-issues §10.8)
2. **Call volume** — per-clause-per-rule NLI (~15 calls/contract) exhausted the
   free-tier per-minute limits. NLI is now **batched**: one `BatchNLIResult` call
   per clause covering all relevant rules + regs (~7 calls/contract).
   `LLM_PROMPT_VERSION` bumped `v1` → `v2` (schema/prompt changed).

`test_live_contract_a_conflict` PASSED on that first run — the pipeline
(LlamaParse → Gemini interactions API → graph → findings) is sound end to end.

### Second live run (2026-09-11): Groq added as primary provider + 4 fixes

The second live run surfaced that Gemini's free tier is structurally too small
(`gemini-3.8/3.7-flash` ≈ 20 requests/day) and that the SDK's own retry loop
wasted ~15 s per call. Fixes (`client.py` largely rewritten):

1. **Groq is now the primary LLM provider**, Gemini the fallback.
   `LLM_PROVIDER_ORDER=groq,gemini` in `.env`. Groq's free tier is ~30 RPM and
   1k–14.4k/day vs Gemini's ~5 RPM / ~20/day. `groq==1.7.0`, OpenAI-compatible,
   JSON via `response_format={"type":"json_object"}` + schema in the system
   prompt (`_strip_json_fences` cleans stray ``` fences). Config:
   `GROQ_API_KEYS` (comma-sep, multi-account) + `GROQ_MODEL_TIERS_RAW`.
2. **SDK-internal retry disabled** — `genai.Client(http_options=HttpOptions(
   retry_options=HttpRetryOptions(attempts=1)))`; Groq client `max_retries=0`.
   The fallback loop now advances on the *first* 429 instead of after 4 retries.
3. **Cooldown memory** — a (provider, account, model) that returns 429/5xx is
   skipped for `LLM_TIER_COOLDOWN_SECONDS` (default 60) instead of being
   re-probed on every subsequent call in the run.
4. **Transient 5xx now advances the chain** — `TransientServerError` for HTTP
   5xx / "high demand" / "try again later" is treated like a 429 (advance +
   cooldown), not raised. A genuinely bad request (400/404, invalid schema)
   still raises immediately.

A wrong model id in `GROQ_MODEL_TIERS_RAW` raises a `NotFoundError` immediately
(by design — config bug, not a quota problem). Fix the list in `.env`.

### Detect over-flagging fix (contract C produced 19 findings on a clean DPA)

- `RELEVANT_REGULATION` / `RELEVANT_PLAYBOOK` narrowed — a clause type is only
  NLI-checked against rules that govern its exact subject (dropped the broad
  "every data-processing clause vs DPDP §8/§4" checks).
- NLI system prompt rewritten to be conservative: "silent on an adjacent
  obligation = NEUTRAL, never CONTRADICTS".
- Cross-clause suppression: a NEUTRAL on a mandatory-protection requirement
  (`dpdp_s9` / `gdpr_art8`) becomes a finding only if **no** clause anywhere in
  the contract ENTAILS it — so contract C's explicit "no children's data"
  clause suppresses the gap finding.
- `LLM_PROMPT_VERSION` → `v3`. Live `contract_c` test relaxed to `<= 3`
  findings (mocked test still asserts exactly 0).

## Phase 2

### Stretch goals — all three built, not skipped

The Phase 2 prompt names Contrarian + Judge + Negotiation Twin as stretch goals,
build-only-if-time-allows. All three were built as part of the core delivery:
Groq's larger free-tier headroom (established in Phase 1) removed the quota risk
that made them a stretch goal in the original design. A "dismissed" Judge verdict
is still persisted (never silently dropped) — see `redline_suggestions.judge_json`.

### Embeddings: lazy, not a one-time backfill script only

The prompt describes embeddings as a one-time backfill. Implemented instead as
**lazy backfill**: `retriever.retrieve_context` calls
`embed_clauses.ensure_embeddings_for_contract` before every vector search, so
embeddings never go stale as new contracts are ingested after this phase. A
standalone `embed_clauses.py` (`python -m app.agents.suggest.embed_clauses`)
still exists for a manual tenant-wide sweep, satisfying the "backfill the
existing sample contracts" instruction for whatever was already in Neo4j.

### Embedding dimension forced to 768

`gemini-embedding-001`'s default output dimension wasn't confirmed against a
live key at build time. Rather than guess and risk an index/query mismatch,
`EmbedContentConfig(output_dimensionality=768)` **forces** every embedding to
768 dimensions regardless of the model's default, and `EMBEDDING_DIMENSIONS=768`
in `.env` matches that when creating the Neo4j vector index. Verified working
end-to-end against real Neo4j (`CREATE VECTOR INDEX` + `db.index.vector.queryNodes`)
with a 768-dim probe vector before this phase was called done — see the
`Confirmed against real Neo4j` note below. If a live embedding call ever returns
a different length, that's a one-line `EMBEDDING_DIMENSIONS` fix (and the index
must be dropped/recreated to match), not a logic bug.

### No Alembic — `Base.metadata.create_all()` for the one new table

`redline_suggestions` (PostgreSQL) is created via `Base.metadata.create_all()`
at FastAPI startup (idempotent, non-fatal like the Neo4j seeding). No migration
framework introduced for a single table. Worth adding Alembic once schema
changes get frequent (a good candidate: Phase 5's tenants/users/roles).

### Confirmed against real Neo4j (not just mocked)

Every new Cypher path — `CREATE VECTOR INDEX`, `db.index.vector.queryNodes`,
`get_override_relationships`, `get_compliance_targets`, `find_finding_by_id`,
`get_clause_by_id` — was exercised end-to-end against the running Neo4j
container with a fake (deterministic, 768-dim) embedding function before this
phase was called done, in addition to the mocked `InMemoryGraphStore` suite.

## Phase 3

### The original-document gap the prompt assumed away

The prompt assumes a `.docx` is already on file for the Executor to edit. Phase
1/2 never persisted the original upload at all (Detect wrote it to a temp dir
and deleted it), and our own test fixtures are PDFs — python-docx can't edit
those. Resolved by:

- `detect/pipeline.py::ingest_and_detect` gained an **optional** `db: Session
  | None = None` parameter (default preserves exact Phase 1/2 behaviour for
  every existing caller/test). When provided, it now captures
  `document_versions` version 1 after a successful Detect run.
- If the upload is already a `.docx`, it's stored byte-for-byte.
- If it isn't (our fixtures, and plausibly many real uploads), a `.docx` is
  **synthesized** from Detect's own structured clause extraction — one
  paragraph per clause, in page order — via
  `agents/fix_and_learn/document_store.py::synthesize_docx_bytes`. This
  guarantees the Executor's exact-text clause matching works against the same
  `raw_text` Detect/Suggest already reasoned about.
- **This is a documented demo-scope simplification**, not a production
  design — a real build would need genuine PDF→Word conversion, or to require
  Word-native uploads for anything headed toward an approval-gated write.

### `approvals.edited_text` — an addition beyond the prompt's literal schema

The prompt's `approvals` table has no column to hold a reviewer's edited
text, but the frontend spec explicitly requires an "Edit" action before
approving. Added `edited_text` (nullable) to `approvals`; when set, the
Executor writes it instead of `redline_suggestions.proposed_text`.

### "Copy then edit" interpreted as one new version, not two

The prompt's steps 2 and 4 read as if the Executor first copies-and-registers
the *pre-edit* file as a new version, then separately saves the *edited* file
as another new version — which would double-count. Implemented as **one**
new version per approval: copy the current version's bytes to a fresh path
(so the current version's own file is never touched), edit the copy, then
register that single edited copy as `version_number = latest + 1`. The prior
version's row and file are provably untouched (asserted by
`test_decide_approved_writes_new_version_and_audit_log`).

### Auto-approval creation wired into Phase 2, not just the API

Per the prompt's "wire this in automatically" instruction,
`suggest/pipeline.py::_run_pipeline` creates the `pending` `Approval` row (+
an `audit_log` row) itself, immediately after persisting the
`redline_suggestion` — not only via a separate manual `POST /api/approvals`
call, which still exists for standalone re-queuing.

### No live test needed for this phase

The Executor and approval-queue logic make no LLM calls at all (pure local
file/DB work) — Phase 1/2's existing live tests already cover the only
LLM-touching step (Suggest, which produces the row Phase 3 acts on), so no
`@pytest.mark.live` additions were needed here.

### Confirmed against real Neo4j + real PostgreSQL (not just SQLite-mocked)

The full chain (Detect -> synthesized v1.docx -> Suggest -> auto-pending
Approval -> Executor guard rejecting a pending approval -> approve -> v2.docx
with both original and proposed text) was run end-to-end against the actual
Neo4j and Postgres containers before this phase was called done, in addition
to the mocked `InMemoryGraphStore` + in-memory SQLite test suite. This also
caught a real bug the SQLite tests couldn't: SQLite doesn't enforce foreign
keys by default, so a cleanup script that deleted `approvals` before
`document_versions` succeeded silently there but correctly failed with a real
`ForeignKeyViolation` against Postgres — confirming the FK constraints are
actually live in production, not just declared in the ORM.

### Post-Phase-3 fix: decided approvals need to stay discoverable

Manual testing surfaced a real UX gap: `/approvals` only fetched
`status=pending`, so the moment an item was Accepted/Rejected it vanished
from the page entirely — taking its "Download document" link with it. A
user's instinct to "re-run the pipeline to get it back" actually created an
unrelated new contract (every `/api/detect` upload mints a fresh
`contract_id`), not a way back to the same document.

Fixed by adding `getAllApprovals()` (no status filter — the backend endpoint
already supported this) and splitting the `/approvals` page into a **Pending**
section (actionable) and a **Decided** section (read-only, status badge,
download link) below it. Locked in with
`test_list_approvals_without_status_filter_returns_decided_items_too`.

## Phase 4

### Scope grew beyond the literal prompt — by explicit request

The Phase 4 prompt specifies 4 routing categories (PORTFOLIO_QUESTION,
SINGLE_DOCUMENT_QUESTION, EDIT_INSTRUCTION, OUT_OF_SCOPE) and no chat
persistence. The build was deliberately expanded, mid-phase, on request:

- **Two extra categories**: `COMPLIANCE_STATUS_QUESTION` (what did Detect/
  Suggest/Fix & Learn actually do — a different retrieval mode: it queries
  Neo4j `Finding` nodes + Postgres `redline_suggestions`/`approvals` directly,
  not vector search over clause text) and `GENERAL_LEGAL_TECH_QUESTION`
  (general legal-tech/regulatory knowledge, answered from the model's own
  knowledge, explicitly NOT portfolio-grounded, no fabricated citations, with
  a "not legal advice" disclaimer).
- **Chat history persistence** — new `chat_sessions` / `chat_messages`
  Postgres tables, `GET /api/ask/sessions` + `GET /api/ask/sessions/{id}/messages`,
  and a real sidebar-plus-thread chat UI at `/ask` (not a single Q&A box).
  Sessions are tenant-wide, not yet per-user — Phase 5 adds login/roles, at
  which point `chat_sessions` gains a `user_id` column.

### Adapting, not literally calling, Phase 2's Retriever

Phase 2's `retrieve_context()` starts from one already-known flagged clause —
it doesn't fit a free-text question. `ask_retriever.py` reuses the actual
shared infrastructure instead: `generate_embedding`, the (now extended)
`vector_search_similar_clauses`, and the lazy-embedding helpers
(`ensure_embeddings_for_contract` / `backfill_all`) from Phase 2's
`embed_clauses.py`.

### `vector_search_similar_clauses` extended (backward compatible)

Added an optional `contract_id` filter (for single-document questions) and
fixed a real correctness gap: Neo4j's vector index returns its top-K matches
*globally* before any `WHERE` filter narrows tenant/contract, so a small K
could silently return too few (or zero) results once filtered. Now
over-fetches (`min(max(top_k*5, 25), 200)`) before filtering and re-limiting.
Also now returns `page_number` (needed for Ask's citations). Existing callers
(Suggest's Retriever) are unaffected — the new parameter defaults to `None`.

### Document-name matching is a simple heuristic, not a fuzzy-match library

`find_contract_by_name()` does substring + word-overlap scoring after
stripping a small set of domain-generic tokens (`contract`, `agreement`,
`document`, `dpa`, `msa`, ...) that would otherwise make every filename look
like a match. Deliberately simple — swap for `rapidfuzz`/`difflib` if this
proves too weak against real filenames in practice.

### Regulation text is always folded into content-question context

Rather than requiring vector search to surface the ~5 seeded `RegulationClause`
nodes, `ask_retriever.py` always appends them to the retrieved context for
every `CONTRACT_QUESTION` — cheap (there are only 3 DPDP + 2 GDPR clauses),
and it guarantees "what does DPDP Section 9 require" gets a real citation
instead of depending on embedding similarity to find it. Regulation citations
use `page_number = 0` (not paginated) — the frontend hides the page number
when it's 0.

### Time parsing for status questions

`status_query.parse_time_reference()` checks a small relative-phrase map
("last week", "this month", ...) first, then a `N days/weeks/months/years`
regex, then falls back to `python-dateutil`'s fuzzy parser. If nothing
parses, it returns `None` (meaning "show everything, most recent first")
rather than erroring — never blocks an answer over an unparseable date.

### Similarity-threshold abstention can't be tested via the fake embeddings

The mocked test suite's fake embeddings are deterministic-but-arbitrary
(hash-derived, all-non-negative components), which tends to produce
artificially high cosine similarity between unrelated texts — so the
threshold branch doesn't naturally trigger under the fakes. Tested instead by
monkeypatching `ASK_SIMILARITY_THRESHOLD` to an unreachable value in one
dedicated test, proving the branch itself works; the *literal* prompt-required
abstention case (unknown document name) is fully deterministic and needs no
such workaround.

### Confirmed against real Neo4j + real Postgres

All 7 response types (contract/portfolio/status/edit/general/out-of-scope/
abstained) plus chat-session persistence were run end-to-end against the real
containers before this phase was called done, in addition to the 15 mocked
tests. Note for anyone doing this again: `list_contracts()` will surface
*every* contract ever ingested into the tenant across every prior testing
session — this is correct, by-design behaviour for a portfolio-wide Ask
agent (Section 4.5 of the project spec: "every contract a company has ever
uploaded... regardless of when"), not a bug, but it does mean old manual-test
contracts will show up in portfolio answers unless deliberately wiped.

## Phase 5

### A Postgres schema gap the phase prompt didn't call out

Phases 2-4 never gave `redline_suggestions`, `approvals`, or `document_versions`
a `tenant_id` column at all — only the Neo4j graph and Phase 4's
`chat_sessions`/`chat_messages` were tenant-scoped. The phase's own exit
criteria ("dashboard endpoints only return data belonging to the requesting
user's tenant") was untestable for approvals/suggestions without one. Added
`tenant_id` to `RedlineSuggestion` (already passed into the Suggest pipeline,
just never persisted) and to `DocumentVersion` (for `/api/documents/*`, given
this build's decision to make document access tenant-isolated, not just
login-gated). `Approval` stays un-denormalized — it's scoped via a join to
`RedlineSuggestion.tenant_id`, which is simpler than keeping a second copy in
sync.

**Because there's still no migration framework**, this is a genuinely
breaking schema change for anyone with an existing dev Postgres volume:
`Base.metadata.create_all()` only creates missing tables, it never alters an
existing one to add a column. Anyone pulling this phase must reset their dev
Postgres volume (`docker compose down -v` under `infra/`) before starting the
backend — see docs/README.md's Phase 5 section for the exact command. This is
a one-time, demo-data-only reset; there's no real user data yet to preserve.

### passlib + bcrypt: the exact same class of pin problem as pydantic in Phase 0

**The bug:** `passlib==1.7.4` (its last release; effectively unmaintained)
reads `bcrypt.__about__.__version__` at import time to detect the backend
version. `bcrypt>=4.1` removed that attribute entirely, so the very first
`CryptContext(schemes=["bcrypt"]).hash(...)` call raised
`AttributeError: module 'bcrypt' has no attribute '__about__'`, masked behind
a confusing second exception ("password cannot be longer than 72 bytes")
because passlib's error-recovery path swallows the real cause.
**The fix, applied:** pin `bcrypt==4.0.1` (last version with `__about__`)
directly in `requirements.txt`, rather than relying on `passlib[bcrypt]`'s
extra, which floats to the latest bcrypt and re-triggers this. **Same lesson
as Phase 0's pydantic/psycopg2 pins: an unmaintained package's stated
dependency range can't be trusted against a dependency that's still receiving
releases — pin the transitive dependency explicitly once this happens.**

### JWT bearer auth breaks plain `<a href>` downloads

**The bug:** `/api/documents/version/{id}/download` now requires
`Authorization: Bearer <token>`, but the existing frontend used a plain
`<a href={url}>` for the download link — a browser navigation triggered by
clicking a link never attaches a custom header, so every download would have
401'd once auth was retrofitted onto that endpoint.
**The fix, applied (`frontend/src/lib/api.ts::downloadDocumentVersion`):**
fetch the file with the auth header attached (like every other API call),
turn the response into a `Blob`, hand the browser a local `URL.createObjectURL`
link, click it programmatically, then revoke the object URL. `approvals/page.tsx`
now calls this from an `onClick` handler instead of rendering an `<a href>`.
**Any future authenticated file download must use this pattern, not a plain
anchor tag — bearer-token auth and simple browser navigation don't mix.**

### Client-side route protection, not server-side

`AuthGate` (in the root layout) redirects to `/login` when no valid,
unexpired JWT is found in `localStorage` — a client-side check, matching this
build's demo scope. It is not a security boundary: the actual security
boundary is the backend re-verifying the JWT signature on every request
(`get_current_user` / `require_role`), and that boundary is real regardless
of what the frontend does. A production deployment would add server-side
route protection (e.g. Next.js middleware checking a cookie) as defense in
depth, but a determined user editing `localStorage` in devtools can only ever
make the *frontend* behave oddly — they still can't get the API to accept a
token they didn't legitimately obtain from `/api/auth/login`.

### Email notifications (Resend) are wired but need a real API key to activate

`app/agents/notifications/notify.py` attempts an email to every reviewer/admin
in the tenant when a HIGH-severity finding is created, but only if
`RESEND_API_KEY` is set in `backend\.env` — left blank (the default), it
degrades to in-app-only notifications, same graceful-skip pattern as every
other optional third-party key in this project. Without a verified sending
domain, Resend's sandbox sender (`onboarding@resend.dev`) can only deliver to
the email address the Resend account itself was created with — fine for this
project's single demo reviewer account, not for multiple real recipients.
**Not covered by an automated live test** — sending a real third-party email
during any pytest run (mocked or live) would be a genuine testing-discipline
violation, so `test_high_severity_finding_creates_notification_row` forces
`settings.resend_api_key = ""` via monkeypatch regardless of what `.env`
holds. Email delivery itself is a manual verification step only.

### Per-user draft rate limiting — Redis's first real use in this project

Added after a design discussion during manual testing: any role may draft an
edit (via Suggest or Ask's edit-instruction handoff) since drafting never
writes to a real document — but nothing stopped one user from flooding the
approval queue with unlimited drafts. Rather than restricting *who* can draft
(which would make the `end_user` role purely read-only and doesn't match how
a real compliance team works — the person who spots an issue isn't always
the person authorized to approve the fix), this caps *how many* drafts one
user can queue per window: 10 per 10 minutes by default
(`DRAFT_RATE_LIMIT_MAX` / `DRAFT_RATE_LIMIT_WINDOW_SECONDS`).

Backed by Redis — the `infra/docker-compose.yml` container and `REDIS_URL`
setting have existed since Phase 0 but were never actually used until now.
`app/core/rate_limit.py` follows the same two-implementation pattern as
`GraphStore` (Neo4j vs. in-memory): `RedisRateLimiter` for real use,
`InMemoryRateLimiter` so the mocked test suite never needs Docker. If Redis
is unreachable, it fails **open** (allows the request, logs a warning) rather
than blocking drafting entirely — consistent with how every other optional
piece of infra in this project degrades (Neo4j/Postgres connectivity checks
at startup, the LLM cache, Resend email).

Applied at two call sites: `POST /api/suggest/from-finding/{id}` and
`POST /api/suggest/standalone` (as a FastAPI dependency,
`enforce_draft_rate_limit`, swapped in for the plain `get_current_user`
dependency), and Ask's `EDIT_INSTRUCTION` route inside
`app/agents/ask/pipeline.py::_route` (a direct function call, since that code
path isn't behind FastAPI's dependency injection) — the latter needed
`handle_ask`/`_route` to gain an optional `user_id` parameter threaded down
from the JWT, since Ask's chat sessions are tenant-wide, not per-user
(Phase 4 anticipated exactly this: see the `ChatSession` docstring). Returns
a real `429` with a `Retry-After` header from the REST endpoints; from Ask,
a new `AskResponseType.RATE_LIMITED` structured response, consistent with
Ask never letting an exception reach the API layer for an expected outcome.

### Chat sessions were tenant-wide, not per-user — found by manual testing

**The bug (found by the user during Phase 5 manual testing):** logging in as
the reviewer account could see and replay the end_user account's Ask
conversations, and vice versa. `ChatSession` (Phase 4) only ever had
`tenant_id` — Phase 4's own docstring even flagged this ("not yet per-user —
Phase 5 adds login/roles, at which point this gains a `user_id` column"),
but the column never actually got added when Phase 5 was first built.
**The fix, applied:** added `ChatSession.user_id` (nullable, so a pre-Phase-5
row surviving a schema reset doesn't violate a constraint), threaded
`user_id` through `handle_ask`/`_get_or_create_session` (reusing the same
parameter already added for per-user rate limiting), and scoped every
session query — `GET /api/ask/sessions`, `GET /api/ask/sessions/{id}/messages`,
and reusing an existing `session_id` on a new `POST /api/ask` — by
`(tenant_id, user_id)` together, not tenant alone. A `session_id` that exists
but belongs to someone else now 404s rather than being silently replayed or
silently hijacked into a new conversation.

### Closing the loop: requester-targeted decision notifications

Added on request, after Phase 5's core build: previously, once a reviewer
decided a pending approval, the person who originally requested that draft
(via Suggest or Ask's edit-instruction handoff) had no way to find out what
happened to it — approvals/notifications were either reviewer-only UI or
tenant-broadcast, with nothing addressed to a specific requester.

- `RedlineSuggestion.requested_by_user_id` (nullable) tracks who asked for
  each draft, set from the JWT at the two creation points
  (`/api/suggest/from-finding/{id}`, `/api/suggest/standalone`) and Ask's
  edit-instruction handoff. Nullable so pre-existing drafts, or ones from a
  direct pipeline call with no authenticated caller, simply skip the
  decision notification rather than guessing a recipient.
- `Notification` gained `kind` (`new_finding` broadcast tenant-wide, vs.
  `approval_decided` addressed to one `recipient_user_id`) and
  `document_version_id` (set on any 'approved' outcome, so the requester can
  download the new version directly from the bell — the download endpoint
  is tenant-scoped, not role-scoped, so this works for an end_user too,
  without needing access to `/approvals`).
- Three distinct outcomes, in `app/agents/notifications/notify.py::notify_approval_decision`:
  rejected (with the reviewer's note), approved-as-drafted, and
  approved-but-reviewer-edited (a different message, since the requester's
  exact wording wasn't the one that shipped) — determined by comparing
  `Approval.edited_text` against the original `proposed_text`.
- Skipped if the requester is the same person who decided it — no point
  notifying a reviewer about their own decision on their own draft.
- **Found while wiring this up**: the frontend's "Reject" button never
  actually collected a reason at all, even though the backend's
  `DecideRequest.note` field already existed and was already displayed back
  to the reviewer afterward (`Note: {reviewer_note}` on a decided item). The
  note was always `undefined`. Added a reveal-a-textarea-before-confirming
  flow (mirroring the existing "Edit" button's pattern) so a reviewer
  actually writes something before rejecting.

## Phase 6

### Horizon-Scanning must be additive, never `replace_findings`

The single most important correctness decision this phase: `GraphStore.replace_findings()` (used by Detect since Phase 1) `DETACH DELETE`s every existing `Finding` node for a contract before writing new ones — it's a full replace, not a merge. If Horizon-Scanning had called it, re-scanning an already-reviewed contract against a new regulation clause would have silently wiped out every finding Detect originally raised on that contract. Added a new, additive `GraphStore.add_findings()` instead — it diffs against already-existing `finding_id`s and only writes genuinely new ones, returning just those new ones so the caller knows what to notify about. This also makes re-running the exact same simulated update idempotent (a real concern: an admin could plausibly click "simulate" twice).

### Reusing Detect's own finding-creation logic, not duplicating it

Per the phase prompt's explicit instruction, `detect_agent.py`'s `_finding_from` helper (renamed `build_finding_from_nli`, dropped its leading underscore) and `_finding_id` (renamed `finding_id`) are now imported directly into `app/agents/horizon_scanning/rediff.py`. A Horizon-Scanning finding and a Detect finding are therefore structurally identical rows in storage — same fields, same severity rule (`HIGH` for any `regulation`-kind finding, matching Detect's own convention for both `CONTRADICTS` and a mandatory-gap `NEUTRAL`), same deterministic id derivation. `notify_new_findings` (Phase 5) is called unmodified — Horizon-Scanning findings ride the exact same notification path as Detect findings, including HIGH-severity email.

### No new embedding storage needed for `RegulationClause`

`generate_embedding()` already works on arbitrary text, so a newly-added regulation clause's embedding is computed on the fly at re-diff time rather than persisted on the `RegulationClause` node. Simpler, and avoids extending the Neo4j vector index (which is built on `:Clause.embedding` only) to a second node label.

### `add_regulation_update`'s signature matches the phase prompt exactly — no `section` parameter

The prompt's literal signature is `add_regulation_update(regulation_name, new_clause_text, effective_date)` — no `section`, even though every seeded `RegulationClause` has one (`"Section 9"`, `"Article 8"`, etc.). Rather than adding an unrequested field to the public API, `section` is derived internally as `f"Amendment effective {effective_date}"` so the resulting clause still has a coherent, displayable section label without expanding the request contract beyond what was asked for.

### Restore needed its own table, not a reuse of `Approval`/`RedlineSuggestion`

`Approval.redline_suggestion_id` is a hard foreign key to `redline_suggestions.id`, and `RedlineSuggestion` carries fields (`proposed_text`, `rationale`, `contrarian_json`, `judge_json`, `negotiation_json`) that describe an AI-drafted redline — none of which fit "revert to version N." Built the parallel `restore_requests` table + `POST /api/restore-requests/{id}/decide` endpoint the phase prompt itself suggested as the alternative, mirroring `Approval`'s shape (`status`, `reviewer_note`, `decided_at`) but with its own restore-specific fields (`target_version_id`, `abuse_flagged`). A new `app/agents/restore/executor.py` is the restore-equivalent of `fix_and_learn/executor.py` — same one-entry-point rule, but simpler: no text edit at all, just `shutil.copy2` of the target version's file forward as a brand-new version number, so the full history is never shortened (restoring v2 while at v5 produces a new v6, not an overwrite of anything).

### Closing the loop for Restore too (beyond the literal prompt)

Per the same pattern Phase 5 established for Suggest drafts (see `docs/PactScan_AI_Ideas_And_Scope_Additions_Log.md`), a restore requester now gets a targeted notification when their request is decided — `notify_restore_decision()` mirrors `notify_approval_decision()`: rejected carries the reviewer's note, approved carries a direct download link to the new version. Not asked for by the literal Phase 6 prompt; added on request for consistency once the feature was pointed out as a natural extension of the existing pattern.

### A missing `admin` seed account, found before it could block manual testing

Horizon-Scanning's trigger endpoint is `require_role(["admin"])`-gated, but Phase 5's seeded demo accounts only covered `end_user` and `reviewer` — there was no way to manually test this endpoint at all without first registering an admin account by hand. Added a third seeded demo account, `admin@demo.pactscan.ai` (same password as the other two), to `app/db/seed_auth.py`.

### New frontend page: `/contracts/[id]`

Neither Part A ("link to each affected contract's findings") nor Part B ("list all versions on the contract detail page, offer Request Restore") had anywhere to live in the existing frontend — there was no contract-detail route at all before this phase; document-version listing was previously only ever embedded inline inside `/approvals`, showing just the single latest version. One new page serves both needs: current findings (via the existing `GET /api/detect/{contract_id}`) plus full version history with a Request Restore action on every non-current version.
